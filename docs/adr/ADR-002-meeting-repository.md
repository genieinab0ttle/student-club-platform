# ADR-002: Use the Repository pattern for meeting data

Status: Accepted

## Context
The meeting feature creates meetings and lists them. Both operations need the database.
We want HTTP handling, business rules and database access to stay in separate classes,
as planned in our layered architecture (ADR-001).

## Decision
We use the Repository pattern. MeetingRepository extends Spring Data's
JpaRepository<Meeting, Long>, and Spring generates its implementation at runtime.
MeetingService gets the repository through its constructor, checks the date rule,
and calls save() and findAll(). MeetingService never writes SQL.

## Participating classes
- MeetingRepository: the repository interface
- JpaRepository<Meeting, Long>: Spring Data interface that provides save() and findAll()
- Spring Data JPA implementation: generated by Spring at runtime
- MeetingService: the client that uses the repository
- Meeting: the entity that is stored (table: meetings)

See docs/architecture/Winx_class_diagram_M3.png.

## Simpler alternative
The controller could call JPA directly. That needs fewer files for a small demo,
but HTTP code, business rules and database code would be mixed in one class,
and the service could not be tested with a fake repository.

## Consequences
Positive:
- Database access is in one place, separate from HTTP and business rules.
- We do not write basic SQL by hand; Spring provides save() and findAll().
- A service unit test could replace the repository with a mock.

Negative:
- The code depends on Spring Data.
- There is one more layer to understand.
